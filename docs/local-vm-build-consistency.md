# 本地与虚拟机构建代码一致性要求

## 1. 强制要求

本地和虚拟机之间发生代码同步或构建时，必须保证两端使用的构建代码完全一致：

- 本地修改已验证通过后，才能更新到虚拟机；更新完成后，必须再次确认虚拟机中的构建代码与本地验证时的代码相同。
- 虚拟机修改代码后，必须先将修改同步回本地并完成一致性确认，才能继续以本地代码构建、测试或提交后续修改。
- 未经同步和一致性确认，不得在本地和虚拟机分别继续修改同一份代码，也不得使用两端不同的代码进行构建结果对比或部署。

这里的“构建代码”包括源码、构建脚本、项目配置、依赖锁定文件、数据库迁移文件、前端依赖清单以及其他会影响构建结果的版本化文件。

## 2. 同步与验证流程

每次本地与虚拟机之间同步代码时，按以下顺序执行：

1. 确定本次同步的来源端，并记录分支、提交号和未提交修改。
2. 将来源端的全部构建代码同步到目标端，包括已修改文件和新增文件；不得只复制部分文件。
3. 在目标端检查分支和提交号，并对工作区差异进行比对。必要时使用文件清单或哈希值确认内容一致。
4. 只有在比对结果确认一致后，才允许在目标端执行构建、测试、部署或生成镜像。
5. 保留本次同步的提交号、代码哈希或差异检查结果，作为构建和部署记录的一部分。

如果发现任一文件不一致，必须先停止构建和部署，完成同步或明确处理冲突后重新验证。

## 3. 一致性的判定标准

以下条件必须同时满足：

- 两端处于同一分支或明确对应的同一提交。
- `git status`、提交差异和未跟踪文件清单符合预期。
- 所有构建相关文件内容一致；文件权限、换行符或编码差异不得导致构建输入发生变化。
- 两端不存在未同步的本地修改或虚拟机修改。

机器专属的密钥、日志、缓存、运行时数据等不属于构建代码，可以按环境单独配置；但任何会参与编译、打包或生成镜像的配置都必须纳入一致性检查。

## 4. 责任与记录

执行同步、构建或部署的人员负责在操作记录中注明：同步方向、来源端、目标端、提交号或代码哈希，以及一致性检查结果。构建失败或结果异常时，优先检查本地与虚拟机的代码一致性，再进行其他排查。
